# 换装与细分修改的卡顿／黑屏分析

后续实现已完成，见[优化执行记录](scene_rebuild_optimization_execution_cn.md)。本文保留优化前基线与当时建议；细分界面以用户后续要求为准，已合并为一个“渲染细分等级”。

日期：2026-09-24。本轮完成源码定位、最近会话日志分析和副屏定量复测；仅增加诊断能力，尚未实施渲染策略优化。正式 `out/DazFastViewer.exe` 的 SHA256 与上一轮发布清单一致，诊断程序单独位于 `out/DazFastViewer-profile.exe`。

## 结论

存在明显改进空间。当前新增／删除服装和修改细分都会进入**完整场景重建**，重复执行全场景绑定、形变／碰撞、细分、材质和渲染设备同步。顶点变化本身需要更新相关几何和加速结构，但不要求销毁整个渲染会话，也不要求重复计算没有改变的基础形变。

本次主要瓶颈是 CPU 碰撞重算和完整 Cycles 场景同步；没有观察到物理内存或显存容量耗尽。黑屏则来自显示资源随会话一起销毁，新会话没有可显示的旧图。这两个问题需要分别处理。

### 耗时分解

以“最终渲染细分 1 → 2”的 11.34 秒为例：

| 阶段 | 耗时 | 说明 |
| --- | ---: | --- |
| UI 复制文档及提交 | 0.089 秒 | 当前在 UI 线程深复制 Document |
| 销毁旧会话 | 0.346 秒 | 其中取消约 0.001 秒，主要是资源释放 |
| 场景复制、选择区域、运行时重建 | 0.963 秒 | 其中形变运行时构造 0.709 秒 |
| 初次形变求值 | 4.720 秒 | **其中碰撞／平滑 4.584 秒** |
| 新 Session 构造 | 0.138 秒 | 尚未上传完整场景 |
| Adapter 完整加载 | 0.828 秒 | 其中全场景细分构建 0.495 秒 |
| Cycles 场景同步 | 4.096 秒 | 内核加载、几何／BVH、图像及设备数据更新 |

表中各阶段之外还有调度、首帧渲染与显示等开销；选择／高亮更新与设备同步部分并行，不应把所有日志计时机械相加。子项已包含在父项中。

四次细分修改的碰撞耗时为 4.58～4.69 秒；添加服装后为 6.11 秒，删除一件后为 5.28 秒。服装文件解析、参数／骨架准备、合并和绑定校验合计为 1.33 秒，其中合并与校验为 1.05 秒。因此本次换装的多数等待发生在文件准备完成之后。

每次重建的进度日志均出现内核加载、图像加载和 OptiX 加速结构构建；图像包括原有人体／头发贴图。它们不是本次衣服新增的全部资源。4.0～4.2 秒是完整场景同步的墙钟时间，不能全部解释成显存拷贝、磁盘读取或内核编译。Cycles 自带 `Update statistics` 在本版本只覆盖部分作用域，本报告未用其中的 `device_update` 数字替代完整同步计时。

### 内存观测

约每 0.5 秒采样一次进程和显卡状态，采样还包含 `nvidia-smi` 调用时间：

- 进程工作集最大约 5.40 GiB，私有提交内存最大约 10.77 GiB；二者不是同一个指标。
- 系统可用物理内存最低约 46.31 GiB。
- 整张显卡的已用显存最大 6,893 MiB，总量 16,376 MiB；包括桌面及其他程序，不是进程独占值。

这些是观测到的采样峰值，不能排除采样间隙的短暂峰值；但结合充足余量和明确的阶段耗时，本次证据指向重复工作，而非容量不足。更高细分会进一步放大顶点、三角形和缓冲区规模，容量风险仍取决于实际资产。

## 源码中的原因

1. [set_subdivision](../src/editor/main.cpp) 为所有细分字段创建新的 `Document`，再调用 `set_document`；没有区分最终渲染参数、视口拓扑参数和实际未变化的值。
2. [Renderer::run](../src/editor/renderer.cpp) 除“同世代参数目录刷新”外，把新的文档指针视为完整替换，执行 `cleanup()`，销毁形变运行时、选择结构、Adapter、Session 和显示资源。
3. 新的 `DeformationRuntime` 没有旧求值状态，因此无法命中已存在的形状／碰撞复用路径；显示细分没有改变基础身体、服装形状，也会重新计算碰撞。
4. [CyclesAdapter](../src/cycles/adapter.cpp) 的 `load()` 重建全部细分和材质。现有 `Delta` 支持位置、实例、可见性等更新，但没有网格拓扑替换及对象增删命令，需要扩展才能复用会话完成换装／细分。
5. [Display](../src/viewport/display.cpp) 能在同一个显示驱动中保留有效帧，但 Session 销毁会释放这些纹理。新驱动在第一帧到来前直接返回，渲染循环却仍清空背景并交换缓冲，形成可测量的空画面。
6. [附件挂接](../src/editor/attachments.cpp) 在发布前构造完整运行时作校验，渲染线程随后又构造一次。校验需要保留，但可以拆分纯关系／拓扑检查与昂贵绑定，或复用已验证的不可变绑定数据。

最近两个用户会话也有同样特征：`editor-20260924-121633-985` 共四次会话创建（含初次加载），每次创建后到首帧约 4.46～5.23 秒；更早一场初次同步为 9.86 秒。旧日志没有记录每次操作输入，不能把其中两帧之间的所有空档当作卡顿，也不能精确区分哪次是细分、换装或删除。汇总见 `artifacts/rebuild-profile/existing-sessions.json`。

## 建议实施顺序

1. **分离细分设置的影响范围。** 最终渲染专用级别只保存参数，不重置当前视口；相同值直接返回。视口细分变化保留基础形变、Fit To 与碰撞结果，只重建受影响网格的细分结果。这是本次证据最充分的优化点。
2. **保留 Cycles 会话，支持局部拓扑更新和对象增删。** 未变化的材质、贴图、对象和基础网格继续复用；只上传受影响网格并重建对应 BVH。不能将新拓扑直接塞进旧的顶点位置更新接口。
3. **把最后有效画面的寿命与 Session 解耦。** 新资源准备期间继续显示旧帧，并明确显示“正在更新”。这可消除空画面，但本身不会缩短碰撞、加载或同步耗时。无需为保留一张图同时保留两套完整 GPU 场景。
4. **换装按依赖更新绑定与碰撞。** 新服装完成后台解析后，只初始化新增对象和受影响的宿主／附件链；避免重复重建已有附件的绑定。GeoGraft 遮盖面和接缝、嵌套头发、删除时引用关系都必须纳入变化范围。
5. **最后再处理交互调度与内存复制。** UI 深复制移到后台，连续细分输入合并到最新值；构建和显示分离以保持响应。低清预览主要减少采样时间，单独加它无法消除这里约 4.6 秒碰撞和 4 秒完整同步。

最终渲染专用字段应消除这轮视口重建。其他操作的提速程度需要完成上述增量路径后，用相同资源再测；当前不承诺毫秒级换装或固定倍数。
